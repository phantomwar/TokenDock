## The one thing that blocks a feature

**Antigravity remote sign-in fails on its last step.** Everything upstream of it
succeeds against live Google: the OAuth exchange, the account lookup, and the
Cloud Code provisioning call returning 200 with the account's real data. The
attempt then fails before the credential is written, in one of four steps that
were not individually logged at the time.

**The next action is one run.** Launch the Debug build, attempt a sign-in, and
read the log. Each of the four candidate steps now logs its own line, and an
unrecognised error type now prints its name, so the failure will be attributed
rather than stopping one line short of the answer:

```
cd tokendock
flutter build windows --debug
.\build\windows\x64\runner\Debug\tokendock.exe `
  -RedirectStandardOutput "$env:TEMP\td.log" `
  -RedirectStandardError  "$env:TEMP\td.log.err"
```

Watch for the `Antigravity:` lines. `monitor.ps1` in the temp directory does this
and tails for a fixed window.

**Do not use `flutter run` for this.** It never exits, so as a tool call it dies
at the timeout and takes the app with it. Launch the built exe directly.

## What is verified, and what is not

**Verified by running it:** the Windows release build, the multi-account
integration test against the real `%LOCALAPPDATA%` database, the widget close
button terminating the process, and — against live Google — the Antigravity OAuth
exchange, the `userinfo` account lookup, and `loadCodeAssist` returning real
account data.

**Not verified:** a complete Antigravity sign-in. No fixture in this repository
is a live Google response and no automated test contacts Google. Every shape
learned was read out of a real Debug log or a real browser page.

**Not exercised at all:** the four API-key providers (`openrouter`, `minimax`,
`opencode-go`, `zai`) against their live endpoints, and the Antigravity *local*
sources.

## Open items, in the order they are worth doing

### 1. Attribute the Antigravity sign-in failure

One run. The instrumentation to do it is committed and verified.

### 2. Correct the Antigravity quota path, which is wrong in three known ways

None of these block sign-in; all of them produce wrong quota data afterwards.

- **`onboardUser` sends no tier and never polls.** It is a long-running
  operation. `oh-my-pi` sends `tierId: "free-tier"` and polls
  `GET /v1internal/{name}` every second for 30s; `CLIProxyAPI` sends **`tier_id`** —
  snake_case, a different field name — and polls 5× at 2s. The metadata differs a
  third time: `CLIProxyAPI` sends three snake_case fields where the others send
  one. Three incompatible shapes, and **no live account has reached this path**,
  because every account tried already carries a tier. Needs a decision, not a
  guess.
- **`paidTier` is the real paid-account marker and is ignored.** `oh-my-pi` tests
  for it; `CLIProxyAPI` reads `paidTier.id` and `paidTier.availableCredits` for
  its balance report. The account used in testing **has** a `paidTier`, so the
  tier TokenDock reports is probably wrong.
- **Free-tier ineligibility is not surfaced.** `oh-my-pi` inspects
  `ineligibleTiers` and gives the user a `validationUrl` they can act on.
  TokenDock would report a generic failure for an account that is simply not
  eligible.

### 3. Discover the `User-Agent` version rather than pinning it

`oh-my-pi` and `CLIProxyAPI` both fetch it from Google's own update manifest.
TokenDock, `cortexkit` and `9router` pin a constant, which goes stale silently —
and a pinned version the server stops accepting is a `400` with no explanation,
which is the exact failure mode the other two defend against.

### 4. The window restores off-screen

PRD §60 requires moving a window to the primary display when its monitor no
longer exists. There is no `Screen`/`bounds` handling anywhere in `lib/`, and the
app was observed restoring itself at x=5406 on a second display spanning
1920–5360 — entirely off-screen, unreachable until dragged back. Small and
well-specified.

### 5. Hide-to-tray as an in-window action

PRD §10 specifies a close button that hides. The window is frameless so the `X`
had nothing to attach to, and the header now carries a close button that *quits*
instead. Hide is reachable from the tray only. A deviation, recorded in PRD §10.

### 6. Gemini CLI / Gemini API

The most valuable item on the 0.3 roadmap, and blocked on a decision rather than
on work. It reuses the `v1internal:*` surface Antigravity already consumes, so
the quota side is close to free — but it needs its own OAuth client, and it
obtains higher rate limits by presenting the official Gemini CLI `User-Agent`.
That is a terms-of-service call for the maintainer. **Not decided, therefore not
built.**

### 7. The embedded OAuth client secret

The maintainer chose to allow it, accepting permanent public disclosure of
Google's credential. **A credential change has no in-app breakage policy**, unlike
a schema change, which tombstones per connection and preserves the cache: a
rotation would break login for every installed copy at once and the fix would
arrive in a release. Running the maintainer's own Google Cloud credentials, read
at runtime, is the route to revisit if that happens.

### 8. Deferred, unchanged

Installer, release 0.1, notifications, groups, drag-and-drop, auto-start, history
and charts. Also undecided: adaptive polling, cross-account fallback, and the
account-binding cross-check described below.

## The two decisions that are genuinely open

### The account-binding cross-check was given up

It was the only defence in the ecosystem against a token for one account reading
another's quota — a failure that produces plausible output rather than an error.
All five reference implementations accept the same loss, because none of them ever
had the check. TokenDock is the only one that had it and removed it deliberately,
having proved the second source does not exist: **Google sends no account id
anywhere on this path**, and the field existed only in TokenDock's own fixtures.

Restoring it needs the `id_token`, whose payload carries the subject and the
email — a genuinely independent second source. It requires adding `openid` to the
five registered scopes, and a wrong scope set is what caused the very first
attempt of this whole sequence. That trade is the maintainer's.

### String versus numeric metadata enums

`9router` sends numeric enums (`ideType: 9, pluginType: 2`); the other four send
strings. Its issue #1226 argues that inconsistent fingerprints get accounts
blocked and reports itself unpatched. TokenDock's identity is now consistent
across every call, so the specific problem does not apply — but nobody has
settled the enum question with evidence, and the one implementation arguing for
numbers has an open bug report behind it.

## Two lessons from this session, written down because they cost real time

**Three of the nine failed attempts failed because of a fix applied in an earlier
one.** A three-field body that declared the client to be the Gemini CLI; a
`userIdentifier` the endpoint does not accept; two headers no implementation
sends. In all three the reference was to hand and had been read only partially,
and in all three the response was `400 INVALID_ARGUMENT` — which names a symptom
and never a cause.

The rule is now in the code and the tests: **for an endpoint that answers
`INVALID_ARGUMENT`, copy the exact request shape from an implementation that
works, field by field, and assert the exact set** — not the presence of the fields
you expect. `cloud_code_headers_test.dart` asserts
`headers.keys == {Authorization, Accept, Content-Type, User-Agent}` and
`body.keys == ['metadata']`, so an extra field fails even when the correct ones
still pass.

**A fixture that invents the field the code reads hides the bug.** The identity
was `email|accountId` for four attempts, with the `accountId` in the fixtures and
in no Google response. CI was green because of it. The same thing happened with
`accountEmail` and `accountId` invented into the *token* response. When a
provider's real response is known, a fixture that agrees with it is worth more
than a fixture that makes the code pass.

## Testing conventions this repository follows

- Tests are written before the change and the run is watched to fail. A test that
  has never failed has not been shown to test anything.
- When an existing test encodes old behaviour, it is corrected **with the reason
  at the site**, not worked around. Several in this session did exactly that, and
  each correction names the reference it came from.
- `flutter format` is run only on the files a change touches. Thirty-six files in
  the tree are deliberately left unformatted; a blanket format is a
  pure-whitespace commit and is its own change, never a side effect.
- A test asserting only that *something* is true passes for any implementation.
  Assert which control holds focus, which key is present, the exact set — not the
  absence of a crash.
