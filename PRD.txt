# Plano de Desenvolvimento — TokenDock Desktop

**Produto:** TokenDock
**Plataforma inicial:** Windows 10/11
**Stack:** Flutter + SQLite + Secure Storage (encrypted at rest)
**Arquitetura:** aplicação local, processo único
**Objetivo:** widget leve para monitorar múltiplas assinaturas, contas e API keys de serviços de IA.

> **Status da primeira meta funcional: implementada e mesclada. Auditoria de corretude e acessibilidade de 2026-09-26 CONCLUÍDA: 36 de 36 achados fechados, cada um com o commit que o fechou. Verificação atual: `flutter test --no-pub` 417/417 (`431e2ca`) em três execuções consecutivas, `flutter analyze` 0 erros/0 warnings/31 infos, `flutter build windows --release` **bem-sucedido** (158s, `tokendock.exe`, 8 warnings de plugin de terceiros e zero neste repositório) e `integration_test/multi_account_flow_test.dart` **3/3** no device `windows-x64` — ambas as execuções primeiras absolutas. Continuam por verificar: integração real com Google/OpenRouter, browser externo e processo Antigravity (todos os testes usam fixtures sanitizadas). Checkpoint: `docs/checkpoints/2026-09-26-correctness-checkpoint.md`.**
> Funciona hoje: widget Windows 10/11 x64 (compacto/normal/expandido), janela frameless com tray e fechar-para-tray, conexões OpenRouter independentes sem limite configurado de quantidade, seleção de providers, fontes locais Antigravity keyless, login Antigravity Google remoto, cancelamento, reconnect in-place, CRUD com test-before-save para OpenRouter, cache SQLite em `%LOCALAPPDATA%\TokenDock\tokendock.db`, segredos via `flutter_secure_storage` encriptados em disco (não é DPAPI, ver `PRODUCT.md`), refresh manual/periódico com no máximo quatro requisições simultâneas e coalescência por conexão, temas claro/escuro/alto contraste, navegação por teclado e Ctrl+R.
>
> Garantias agora verificadas por teste: o custo de leitura é independente da quantidade de contas (`getById`, `getAllWithHealth`, `getAllForAll`); a troca de credencial é single-flight por conexão tanto no serviço quanto no provider; o loopback OAuth é exclusivo em IPv4 e IPv6; transporte OAuth e descoberta de sessão local são ambos limitados no tempo; credencial ilegível é reportada em vez de enviada; migrations são retomáveis; linha de cache corrompida degrada em vez de derrubar todas as conexões; e a copy de erro nunca interpola a exceção, portanto SQL, nomes de tabela e texto com formato de credencial não chegam à UI.
>
> Pendências de retomada: integridade de schema (C-23, sem foreign key, índice redundante, coluna morta), paridade entre densidades (C-22), tipografia contra a spec (C-19), o notifier baseado em `Expando` (C-24), código morto e limpeza. Validar ainda uma conta Google real, callback de navegador externo, rotação de refresh token e um processo Antigravity real. Não inferir contratos privados, scraping ou OAuth sem escopo/API oficial.

# 1. Estratégia de desenvolvimento

O projeto deverá seguir três princípios:

1. **Interface primeiro**
2. **Uma integração funcionando antes de adicionar outra**
3. **Não adicionar infraestrutura antes de existir necessidade real**

A sequência será:

```text
UI
↓
Persistência
↓
OpenCode
↓
MiniMax
↓
OpenRouter
↓
Antigravity
↓
Polimento
↓
Release
```

Cada fase precisa produzir uma aplicação utilizável.

# 87. Definição de pronto para uma feature

Uma tarefa só termina quando possui:

```text
implementação
loading state
error state
persistência quando aplicável
teste
UI final
```

Não considerar pronto somente porque:

```text
"API respondeu"
```

---

# 88. Regras para evitar overengineering

Não criar:

```text
interface
factory
repository
service
manager
controller
```

para cada classe automaticamente.

Criar abstração somente quando:

```text
existirem pelo menos 2 implementações

ou

houver dependência externa que provavelmente mudará
```

Exceções que já justificam abstração:

```text
ProviderAdapter
SecretStore
ConnectionRepository
```

---

# 89. Regra para novas dependências

Antes de adicionar pacote Flutter:

responder:

```text
1. Flutter/Dart padrão resolve?

2. O pacote é realmente necessário?

3. Está mantido?

4. Suporta Windows?

5. Há alternativa menor?
```

Se as respostas não forem boas:

não adicionar.

# 90. Regra para novos providers


Nunca exigir mudança nos cards principais.

Se exigir:

revisar o modelo comum.
