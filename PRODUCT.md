# Product

<!-- impeccable:product-schema 1 -->

## Platform

adaptive

## Stack

Flutter desktop application targeting Windows 10/11 x64. The first release does not enable web, mobile, macOS, or Linux targets.

## Users

People who maintain multiple paid AI subscriptions, local accounts, and API keys and need to identify the account with remaining quota without opening each provider dashboard.

## Product Purpose

TokenDock is a lightweight always-available desktop widget that shows the current quota, reset time, connection health, and cached state for several AI-provider accounts. Success is a trustworthy at-a-glance answer to: “Which of my subscriptions still has limit?”

## Positioning

A local, single-process Windows widget that aggregates independently authenticated AI accounts while keeping credentials outside its SQLite database.

## Operating Context

The app is opened from the Windows tray, then remains visible beside everyday work. Users add, test, refresh, edit, enable, or remove provider connections. The app starts from local cache and refreshes in the background, including when a provider is temporarily unavailable.

## Capabilities and Constraints

- Connections are not capped by account count; providers and local resources may impose their own operational constraints. Compact, normal, and expanded widget modes; tray behavior; SQLite cache; encrypted-at-rest credential storage; and manual/periodic refresh are supported. Five providers are registered; **OpenCode Zen remains deferred** because its pay-as-you-go balance has no documented endpoint, while **OpenCode Go is registered** through its own usage route — see the provider note below.
- One local process, one local SQLite database, no server, cloud service, analytics, or plugin system.
- The UI must preserve prior cached values after a fetch failure and must never rely on color alone for status.
- Provider endpoints and response contracts must be established before implementation; they are not guessed from product requirements. Vendor documentation is the first source, but it is **not sufficient on its own** — a contract absent from a published OpenAPI may still exist. See the provider note below for the process this changed.

## Brand Commitments

- The user-provided references in `docs/imagens/` are binding visual evidence: quiet, high-contrast operational interfaces; warm off-white surfaces; near-black anchors; rounded modules; sparse but intentional vivid green/lime emphasis; restrained semantic status color; clean sans-serif typography.
- The interface must stay desktop-native, readable at a glance, and calm enough to remain on-screen all day. It must not become a generic analytics dashboard or a neon/gamified AI interface.

## Implementation Status

- Status: correctness and accessibility remediation implemented. All P0 and P1 findings from `docs/audit-2026-09-25-second-pass.md` are closed; Windows 10/11 x64 only. See `docs/checkpoints/2026-09-26-correctness-checkpoint.md`.
- Provider list: **`openrouter`, `antigravity`, `minimax`, `opencode-go` and `zai`** are registered. OpenRouter uses `AuthKind.apiKey`; Antigravity uses `AuthKind.oauth` and dispatches only explicit `providerData.source` values `language-server` or `agy-cli` to the local reader. Remote is the default and remains available when source is absent or `remote`. MiniMax, OpenCode Go and z.ai are `AuthKind.apiKey`.
- **`OpenCodeSupport` records a corrected conclusion, and the correction is the interesting part.** An earlier revision held that OpenCode Go and Zen were both unregistrable because `GET /zen*/v1/models` returns 200 for an invalid key. That measurement was correct and the conclusion was not: a model catalog is static by definition, so an account-independent answer is correct behaviour rather than a defect, and "the listing cannot gate a credential" does not imply "nothing can". The endpoints that actually meter the account — `GET /zen/go/v1/usage` (401 invalid key, 403 valid key with no Go plan) — were never probed. Go is registered; Zen stays deferred on a better-founded reason, and the reference implementation registers a Go usage provider and no Zen one, so that gap is not specific to this port.
- `Migration001` creates `auth_type`; `Migration003` adds `identity_key` and `provider_data`; `Migration004` rebuilds `quota_cache` to declare `FOREIGN KEY (connection_id) REFERENCES connections(id) ON DELETE CASCADE`, drops the dead `status` column and the index the composite primary key already covered, and adds `idx_connections_sort_order` on `(sort_order, created_at)`. `AppDatabase.open` runs `Migration001`–`Migration004` and then applies `PRAGMA foreign_keys = ON`.
- The pragma is applied **after** the migrations on purpose. `PRAGMA foreign_keys` is a no-op inside a transaction, so enabling it earlier — including through sqflite's `onConfigure`, which fires before the hand-rolled migrations run — would leave enforcement active across the rebuild that declaring the cascade requires, and no statement in that migration can turn it off. Measured: a rebuild with one pre-existing orphan row fails with SQLite error 787. `Migration004` therefore filters orphans out of the copy with `WHERE EXISTS`, which also keeps the migration from aborting, and gates the rebuild on `PRAGMA foreign_key_list` so a run whose DDL committed without its version marker is recognised as already done.
- Migrations stamp `user_version` inside the DDL transaction and gate `ALTER TABLE` on `PRAGMA table_info`, so an interrupted migration is resumable instead of failing on `duplicate column name`.
- Storage reads degrade rather than throw: an unparseable `reset_at`, `last_checked_at` or `cooldown_until` becomes null instead of failing the read for every connection.
- `provider_data` is sanitised through the shared `isSensitiveKeyName` predicate, so `accessToken`, `refreshToken`, `idToken`, `apiKey` and `csrfToken` are all stripped at any nesting depth. Non-secret metadata (`source`, `projectId`, `tier`) is preserved.
- OpenRouter retains quota hardening: 401 invalid credentials, 402 insufficient credits except documented in-flight-budget responses with `Retry-After`, 403 forbidden, and 429/503 honoring valid `Retry-After`; failures preserve cached quotas and redact current credential fields.
- Antigravity local read-only quota is explicit opt-in through the Connections UI. Session discovery is bounded by a five-second budget applied by the reader, and a failed or unresponsive discovery means "no session found" rather than a stalled or throwing refresh. Account mismatch rejection, strict fraction validation, and no credential custody remain mandatory. CSRF values never enter SQLite.
- Antigravity remote OAuth is exposed through the Connections UI with external loopback browser + PKCE, form-encoded Google token requests, least scopes, isolated refreshable secrets, per-connection operation lock, typed failure causes, account guard, quota retrieval, actionable onboarding-required copy, bounded Full Jitter retries after `Retry-After`, rotated-token reuse revocation, durable schema quarantine, and reconnect while preserving cache. The loopback port is bound exclusively on both IPv4 and IPv6, so no other local process can take it. A stored credential that cannot be parsed is reported as unreadable rather than sent as a bearer token. Access, refresh, ID, and CSRF values never enter SQLite. Real Google/browser/process validation remains pending.
- Credential exchange is single-flight per connection in two places: `RefreshService.runTokenOperation` for refresh and probe paths, and the provider for its own test-time refresh, which bypasses the service. A rotating refresh token is now exchanged once per connection, and the grant is revoked only on positive evidence of reuse rather than on any `invalid_grant`. The rotated-token ledger is a bounded 32-entry window.
- Per-connection health is persisted alongside auth metadata. Active cooldowns skip only that connection; successful refresh clears the cooldown. Timer cadence remains fixed; adaptive polling and automatic account fallback are not implemented.
- Connections have no configured count limit. Refresh is manual, Ctrl+R/Cmd+R (disabled while a text field has focus), tray action, and one periodic timer. Connections exposes the persisted 1/3/5/10/manual selector; manual cancels the timer, and other stored values normalize to the 3-minute default. At most four connection refreshes run concurrently and same-ID operations coalesce.
- Read cost is independent of account count: `ConnectionRepository.getById` serves per-connection work, `getAllWithHealth` returns a connection with the health already on its row, and `QuotaCacheRepository.getAllForAll` loads every cached quota in one query. A refresh cycle reads the connections table once instead of once per connection, and startup issues two queries instead of `1 + 2N`.
- Cache-first: cached quotas render immediately; refresh failures preserve prior values and show `Last updated <relative age>` in compact, normal, and expanded modes, and that age keeps counting. Past resets render `Resetting…`. A quota with no provider cap renders `No key cap`, which is distinct from the `Unavailable` used for genuine failures.
- **A failed or incomplete fetch must never report "healthy, no usage data".** `RefreshService` calls `saveAll(connectionId, snapshot.quotas)`, which *replaces* the cached row set, so a healthy-but-empty result would blank the user's card because an endpoint timed out or changed shape. Every provider therefore returns a non-`ok` snapshot in that case, which takes the error path and keeps the last known values and their age. This is pinned by tests in each provider.
- The authoritative quota value renders in full-contrast ink rather than the muted tone reserved for metadata, in both the quota row and compact density. Countdown and cache-age labels tick every 30 seconds, the shortest interval that can change an hours-and-minutes label.
- User-facing error copy never interpolates an exception object. `userSafeErrorMessage` maps known failures to deliberate wording and otherwise returns a fixed per-call-site literal, so SQL, table names, column names, driver codes and credential-shaped text cannot reach the UI.
- Window/tray: frameless 360x600 window, hide-to-tray on close, explicit Exit, and a scrollable widget shell for large connection sets. The tray menu exposes Open TokenDock, Refresh All, Always on Top, Connections, and Exit, with double-click restoring the widget.
- Credentials: UUIDv4 references in `%LOCALAPPDATA%\TokenDock\tokendock.db`; secret values only in `flutter_secure_storage` (`^11.2.0`), which encrypts them at rest into `%APPDATA%\<CompanyName>\<ProductName>\flutter_secure_storage.dat` on Windows, with no Credential Locker. **This is not DPAPI**, despite what earlier revisions said: the plugin applies its own cipher rather than `CryptProtectData`, so the ciphertext is not bound to the Windows account by the OS. `integration_test/secret_store_windows_test.dart` asserts against the real plugin that the plaintext never reaches disk. Saved credentials display a masked preview (leading characters plus a fixed bullet run and the last four), never the full secret.
- **`windows/runner/Runner.rc` no longer ships the Flutter template default.** `CompanyName` was `com.example` — a domain reserved for examples (RFC 2606) — which put the secure storage under `%APPDATA%\com.example\tokendock\`, a path any other template-built Flutter app would also use, and listed `com.example` as the publisher in Windows' file properties. It is now `TokenDock`, so storage lives at `%APPDATA%\TokenDock\tokendock\`. Because the plugin derives that path from the version resource, renaming it alone would have made every already-stored credential read as `null` — the app would look healthy and silently lose the user's keys. `lib/storage/secret_store_migration.dart` therefore relocates an existing store on first launch, and is called from `main` rather than from `SecureSecretStore`'s constructor: the constructor is reachable from the unit suite, and a migration of real credentials must never be a side effect a test can trigger. It never throws, and it refuses to merge when both locations exist rather than guessing which store is authoritative.

- **Providers: OpenRouter, Antigravity (remote OAuth and local keyless), MiniMax, OpenCode Go and z.ai.** All five report quota, and all four newly-verified response shapes were ported from a working implementation in `can1357/oh-my-pi` rather than inferred. Each has a real credential gate, which is the property that makes test-before-save meaningful: MiniMax `GET /v1/models` 401s, OpenCode Go's usage route 401s/403s, z.ai gates on `success` in the body, OpenRouter on `GET /api/v1/key`.
- **Three of the five needed vendor-specific care, and each is a trap worth naming.**
  - **MiniMax answers HTTP 200 even for a rejected credential.** The success signal is `base_resp.status_code === 0`. Trusting the status line would report a pristine quota for a key that does not work — the worst possible failure for a quota widget.
  - **OpenCode Go's usage route is first-party but undocumented**, and the reference implementation records that its shape changed once on merge day. The parse is therefore all-or-nothing and pinned against recorded fixtures, so a reshape costs the user a number rather than showing a wrong one.
  - **z.ai sends the raw key in `Authorization` with no `Bearer` prefix.** Prefixing it would send `Bearer <key>`, be rejected, and leave a credential that is never actually verified while the app reports it broken. `ProviderHttpProbe.getJson` takes a full header value for this case.
- **Antigravity remote OAuth now uses the correct client.** It previously sent `clientId` `681255809395-…`, which is the *Gemini CLI* client, while requesting Antigravity's scopes. An OAuth client is only permitted the scopes registered to it, so Google rejected the login with `Error 400: invalid_scope`, listing the three scopes — which reads as a scope problem rather than a client problem. The Antigravity client is `1071006060591-…`, it is a **confidential** client so both the code exchange and the refresh need `client_secret`, it registers **five** scopes rather than three (`cclog` and `experimentsandconfigs` were missing), they must be sent as full URLs, and `prompt=consent` is required or Google reuses a grant and returns no refresh token — which then fails on the *next* login as "OAuth refresh token missing". Credentials taken from `wiseai/picoclaw` `docs/security/ANTIGRAVITY_AUTH.md`, not guessed.
- **The client secret is embedded, and the maintainer decided to allow it.** The concern was recorded before the decision and is kept on file: the repo is public, a desktop binary is readable, the credential is Google's rather than the maintainer's, and publishing it is permanent. GitHub push protection blocks the commit until the secret is allowed, and the maintainer allowed it so remote Antigravity login works out of the box for every user. The supported alternative — running the maintainer's own Google Cloud OAuth credentials, read at runtime — was not taken, and is the right route to revisit if the credential is ever rotated or if the five scopes change. **A credential change has no in-app breakage policy**, unlike a schema change, which tombstones per connection and preserves the cache: a rotation would break login for every installed copy at once and the fix would ship in a release. See `docs/checkpoints/2026-09-26-correctness-checkpoint.md`.
- **The widget showed one number per account where the reference shows a quota picture.** Four defects, all now fixed and covered by `quota_presentation_test.dart`:
  - **The default window rendered the compact density, permanently.** `WidgetShell` applies 16px of padding per side and the density `LayoutBuilder` sat inside it, so the shipped 360px window measured 328px — under the 330 compact threshold. The breakpoints are specified against the window width and were being compared against the content width, so every size the app is actually used at fell into the least informative layout. `WidgetShellExtent` now captures the width outside the padding.
  - **Only `quotas.first` was rendered.** OpenCode Go reports three windows, MiniMax two, z.ai three, and the window that is actually running out is frequently not the first. Normal density now renders every window, ordered most-exhausted first so the binding constraint is findable without reading every row.
  - **A percentage rendered as `remaining/limit`.** A percent quota's limit is always 100, so it read `88/100 %` — redundant, and ambiguous enough to be read as "88% *left*". A full quota read `100/100 %`, which reads as "100% used" on a connection that has used nothing. It now reads `88% used`, keyed on the unit rather than on `limit == 100`.
  - **"No key cap" was the headline.** A key with no ceiling rendered that in the largest type on the card. The word stays — audit C-31 requires it and a key with no cap should not read as broken — but it is now quiet metadata and no bar is drawn, because an unknown meter must not look like an empty one reading "used nothing".
- **A healthy connection no longer prints its word on every account.** Three accounts each rendering a green `Connected` is the same fact three times, spent on the scarcest real estate. The word is suppressed for `ok`; the glyph and the semantic label remain, and anything needing attention still says so in words. The cache age is likewise stated once rather than per account.
- **The quota figure is 15px and the provider monogram 24px.** The figure was 20px, which overran the 360px window and pushed the window label below it; the monogram was a 32px disc, exactly as tall as the account name it precedes. The 20px was specification-mandated, so the spec is amended and records why. Neither change touches the contrast guarantees — the figure still outranks the metadata beside it (C-19) and still renders in full-contrast ink (C-20), and `figure_scale_test.dart` asserts both floors.
- **A latent overflow was fixed.** The value `Text` in `QuotaRow` was unconstrained, so a legitimately wide absolute meter such as `12345.5/100000 requests` drew a 140px overflow stripe. It was unreachable at 360px precisely because that width never reached the normal density. The value now wraps rather than overflowing, because truncating it would regress C-20.
- **Window position is not validated against the current monitors.** PRD §60 requires that a window whose monitor no longer exists moves to the primary display "to avoid opening off-screen", and there is no `Screen`/`bounds` handling anywhere in `lib/`. Observed directly: the app restored itself at x=5406 on a second display spanning 1920–5360, so the window was entirely off-screen and unreachable until dragged back. **Unimplemented and recorded here rather than fixed in passing.** `RefreshService` calls `saveAll(connectionId, snapshot.quotas)`, which *replaces* the cached row set, so a healthy-but-empty result would blank the user's card because an endpoint timed out or changed shape. Every provider therefore returns a non-`ok` snapshot in that case, which takes the error path and keeps the last known values and their age. This is pinned by tests in each provider.
- **Only a credential rejection revokes a credential.** `ProviderThrottle` is the single taxonomy for refusals, and the rule it enforces is that a usage limit is not a credential problem: a frequency cap, a burst cap, a concurrency cap, a spent window, a spent balance and a busy provider each get a status and a cooldown, and the credential survives all of them. Only an explicit 401 (or a vendor code that means the same) marks it invalid. **An unrecognised code or status is transient and never revokes** — a permissive default costs a cooldown the user did not need, an aggressive one costs them their configuration. The ladder is concurrency 5s, frequency 30s, capacity 45s, server error 20s, spent window 30min, spent balance 30min, adapted from `packages/ai/src/error/rate-limit.ts` in `can1357/oh-my-pi`. `ProviderStatus.fromHttpStatus` delegates here, which removed the duplicate status table whose divergence caused audit C-34.
- **A Reconnect prompt does not outlive the failure that raised it.** A definitive rejection raises `CredentialDisabledEvent` and `AppState` shows a Reconnect action, and a later successful fetch now **takes that prompt back down** (`CredentialEventCause.recovered`). Previously the escalation was cleared only by an explicit user action — edit, reconnect, delete — and never by a success, so one transient 401 left a working key nagging for the rest of the session while the app refreshed it successfully behind the prompt. Recovery is reported at most once per escalation, so it cannot churn the UI on every refresh cycle, and a throttled response is not recovery: the credential was rate-limited, not shown to work.
- **Escalation still happens on the first rejection, deliberately.** A two-stage "suspect then confirm" scheme was implemented and reverted. It would delay the Reconnect action, which is the only way to re-authenticate an OAuth connection — there is no "edit the key" for Antigravity — and a connection whose credential is genuinely dead would sit with no affordance while the app kept failing. The proven defect was the missing recovery, not a too-eager escalation.
- **Classification tokens and user-facing copy are separate values.** `CredentialEventCause` holds the internal tokens (`bare_401`, `invalid_grant`, `credential_recovered`) that drive routing; the `error` persisted as connection health is deliberate copy, via `credentialRejectionMessage`. They were the same string until this was split, and `token_dock_widget` renders `snapshot.error` **verbatim** — so a connection rejected with a bare 401 displayed the literal text `bare_401` on screen.
- This rule caught a defect in this project's own work: the first MiniMax and z.ai adapters mapped *every* non-success body code to `authError`, so a MiniMax frequency cap (code 1002) revoked a working credential and asked the user to re-enter it. Same defect class as C-34, reached through a different door.
- **`limit` and `remaining` must share a scale.** z.ai reports absolute meters (12000 credits) alongside a server-*rounded* `percentage`; deriving `remaining` from that percentage would have rendered `88/12000`. An absolute meter reports both in absolutes, and only a percent-only payload uses 0-100.
- Schema integrity is now enforced by the database rather than by application code: a v3 file is upgraded on disk through a real restart, the declared cascade is asserted via `PRAGMA foreign_key_list`, enforcement is asserted via `PRAGMA foreign_keys`, an orphaned cache row is proven to be purged rather than carried forward, a stale `user_version` over an already-rebuilt table is proven resumable, and the retired column and index are proven gone. Turning the pragma on inside `TestDatabase` also exposed two fixtures that were caching quotas for connections that never existed.
- The three widget densities share one frame and cannot drift: all of them render the cache age and the error line, and a table-driven suite asserts the parity across the three widths. Compact previously omitted the error, so a failing account showed a stale quota number in the default density with no visible reason while the other two densities explained themselves.
- `AppState` is a real `ChangeNotifier` and each instance owns its listener list. It previously delegated to a private notifier found through a static `Expando` while its loading and empty constructors were `const`; Dart canonicalised those, so every loading shell in the process shared one object and one notifier, and disposing one tore down the rest. A test reproduces the original failure and asserts that disposing one state leaves another listening.
- **The whole 2026-09-25 audit is closed: 36 of 36 findings, each with the commit that closed it.** A failed database open now surfaces a retryable, exitable window instead of killing the process before `runApp`. The type ramp matches the spec, with the countdown on its own step so it does not compete with the figure it annotates. A zero quota limit reads as `No key cap` rather than `5/0`. `auth_type` is derived from `AuthKind` and guarded by a source test. Three functions with no production callers are gone. The masked credential uses the spec's fixed bullet run.
- **Not verified:** no real Google integration, external browser launch, Antigravity process, OpenRouter, MiniMax, OpenCode Go or z.ai call was exercised; every automated test uses sanitized fake HTTP and process fixtures. The Antigravity OAuth credentials were corrected from a reference implementation, and the failure this addresses was a real one the user hit in a browser, but a successful login against Google has not been observed. The four ported response shapes come from a working third-party implementation, which is strong evidence but is not the same as a live response from the user's own account. The Windows release build and the multi-account integration test **were** run on 2026-09-26 (see above), but neither contacts a live provider.
- **Not implemented, and deliberately so:** `GitHub Copilot`, `Codex`, `Claude` and the Gemini CLI all appear in the reference implementation's usage providers and in the PRD's 0.3 roadmap, but each needs a *new auth flow* rather than an adapter — a GitHub entitlement token, a per-CLI OAuth exchange, or its own token exchange. Gemini CLI additionally works by presenting the official Gemini CLI `User-Agent` to obtain higher rate limits, which is a product and terms-of-service decision for the maintainer, not an implementation detail. None of these are stubbed or faked; they are simply absent. See `docs/checkpoints/2026-09-26-correctness-checkpoint.md` for the full reasoning and the per-provider blockers.

## Product Principles

1. Cache-first truth: a usable last-known value is more valuable than an empty card during a provider failure.
2. Independent accounts: a connection's credential, result, error, and cache never leak into another connection.
3. Glance before detail: lead with the quota that determines where the user can work next.
4. Local by default: credentials are references in SQLite and values in platform-backed secure storage.
5. Calm operational clarity: visual emphasis marks action or risk, not decoration.

## Accessibility & Inclusion

Meet WCAG 2.2 Level AA contrast for text and essential controls; expose a visible keyboard focus state and logical tab order; retain text and icon/symbol status labels alongside color; honor Windows text scaling, contrast themes, and reduced-motion preferences; keep all core flows keyboard-operable.
